## Atlas UI v0.6 abgeschlossen

### 1. Ausgangspunkt

Plattform v1 war zu Beginn dieses Abschnitts bereits abgeschlossen und
real verifiziert (siehe oben). Ziel von v0.6 war ausdrücklich nicht mehr
der Umbau der Mitte, sondern die vier UI-Räume (Object Explorer,
zentraler Arbeitsraum, Context Inspector, Activity Stream) als
zusammenhängenden Arbeitsraum wirken zu lassen – ohne künstliche
Aktivitätsanzeige oder simulierte KI-Präsenz einzuführen.

### 2. Durchgeführte Änderungen

**Schritt 1 (Commit `14731ce`)** – Object-Explorer-Auswahlübergang
beruhigt: `.object-list-item`-Transition von `0.18s` auf `0.32s
ease-out` verlangsamt. Reiner visueller Zustandsübergang – keine neue
Logik, keine neuen Elemente, keine Datenänderung.

**Schritt 2 (Commit `5ba9b64`)** – Activity Stream von `selectedId`
entkoppelt: neuer, separater State `allWorkSteps`, geladen unabhängig
von der Auswahl über `Promise.all` (ein Aufruf pro Work Item, bereits
vorhandene `getWorkSteps()`-Bridge, keine neue Backend-/Tauri-Funktion).
`workStepActivityEvents()` blieb unverändert – die Einschränkung lag
ausschließlich am Aufrufer. Activity Stream zeigt seitdem Ereignisse des
gesamten Arbeitsraums, nicht mehr nur des aktuell gewählten Work Items.

**Schritt 3 (Commit `7054a22`)** – Activity-Stream-Navigation
hinzugefügt: Klick auf ein Ereignis ruft `setSelectedId(objectId)` auf
(derselbe Mechanismus wie `ObjectExplorer.onSelect`) und führt damit
zurück zum zugehörigen Work Item. Raumverbindung hergestellt, ohne den
Stream selbst wieder von der Auswahl abhängig zu machen – Schritt 2s
Entkopplung blieb dabei unangetastet.

### 3. Architekturentscheidungen

- Object Explorer, Object Editor und Context Inspector folgen weiterhin
  dem aktuellen Auswahlkontext (`selectedId` → `selection` via
  `resolveSelection()`) – unverändert seit vorherigen Schritten.
- WorkSteps bleiben als selektionsgebundener State (`workSteps`) die
  Detailansicht des ausgewählten Work Items (Arbeitslage, „Gemeinsame
  Arbeit") – bewusst nicht durch `allWorkSteps` ersetzt.
- Activity Stream ist jetzt die globale Chronik des Arbeitsraums, klar
  getrennt von der Detailansicht, aber weiterhin fähig, in sie hinein zu
  navigieren.
- Damit beantwortet jeder Raum eine eigene Frage: Object Explorer „was
  gibt es", Object Editor/Context Inspector „was ist das Ausgewählte",
  Activity Stream „was ist im gesamten Arbeitsraum geschehen".

### 4. Tests

- TypeScript-Build (`npx tsc -b`) erfolgreich in allen drei Schritten.
- Produktions-Build (`npm run build`) erfolgreich in allen drei
  Schritten.
- `git diff --check` erfolgreich (keine Whitespace-Fehler) in allen drei
  Schritten.
- Alle Tests mit echten Repository-Daten (u. a. WI-0002, WI-0004,
  WI-0018, real 18 Work Items/52 WorkSteps) über `vite preview` +
  Chrome DevTools Protocol, keine erfundenen Testdaten.
- Auswahlwechsel im Object Explorer geprüft (Vorher-/Mid-/Nachher-
  Screenshots des Übergangs).
- Globale Unabhängigkeit des Activity Streams geprüft: Inhalt vor und
  nach einem Auswahlwechsel war nachweislich identisch (`18`

- Navigation aus dem Activity Stream geprüft: Klick auf einen

### 5. Offene Punkte

Nicht als Fehler, sondern als Kandidaten für künftige Schritte:

- Suchzustände beim Work-Item-Wechsel: `repositoryFilename`,
  `repositoryFileMatches`, `repositoryFileError` (Repository-Datei-
  Suche) besitzen keinen `useEffect` auf `selectedId` und bleiben beim
  Wechsel des Work Items unverändert sichtbar.
- Kontextdatei-Editor und mögliches altes Mutationsziel:
  `contextRefsEditorWorkItemId`/`contextRefsDraft` schließen sich beim
  Wechsel von `selectedId` ebenfalls nicht automatisch – das Formular
  kann nach einer Navigation weiterhin auf ein nicht mehr angezeigtes
  Work Item zielen.
- Weitere Stabilitätsprüfungen: Verhalten von `Promise.all` über alle
  Work Items bei deutlich größerer Work-Item-Anzahl oder bei einzelnen
  fehlschlagenden `getWorkSteps()`-Aufrufen (aktuell: der gesamte
  `Promise.all` schlägt fehl, `allWorkSteps` wird geleert) wurde nicht
  gezielt geprüft.

### 6. Abschlussbewertung

Atlas UI v0.6 verbessert nicht nur die Darstellung, sondern klärt die
Rollen der Räume und verbindet sie über echte Datenzustände – nicht über
zusätzliche visuelle Behauptungen. Keiner der drei Schritte hat Backend,
Tauri-Commands oder Datenmodelle verändert; jede Verbindung zwischen den
Räumen entstand durch Wiederverwendung bereits vorhandener Funktionen
(`getWorkSteps`, `workStepActivityEvents`, `setSelectedId`).

## Erster vollständiger Arbeitskreislauf: WorkSteps → Submission → Repository

### 1. Ausgangspunkt

Plattform v1 war zu Beginn dieses Abschnitts bereits real verifiziert
(siehe oben). UI v0.6 (siehe oben) hatte die vier Räume – Object
Explorer, zentraler Arbeitsraum, Context Inspector, Activity Stream –
zu einem zusammenhängenden Arbeitsraum verbunden. WorkSteps konnten
erstellt (`publishWorkStep`, `generateWorkStep`) und als Arbeitschronik
sichtbar gemacht werden (Activity Stream, „Gemeinsame Arbeit"). Es
fehlte weiterhin der Übergang von gemeinsamem Austausch zu einem
dauerhaften Artefakt: WorkSteps blieben sichtbare Zwischenstände ohne
Weg in ein Submission-/Repository-Artefakt aus der Plattform heraus.

### 2. Durchgeführter Meilenstein

- Submission-Erstellung wurde aus der Plattform erreichbar gemacht
  (neuer UI-Trigger „Submission erstellen" in `Workspace.tsx`).
- Der bestehende `submitStructured()`-Pfad wurde unverändert genutzt
  (`platformBridge.ts` → Tauri-Command `submit_structured` →
  `submit_structured.py` → `submission_adapter.py` →
  `submission_service.submit()`).
- Kein Backend-Umbau: keine Änderung an `validator.py`,
  `submission_service.py` oder `submission_adapter.py`.
- `base_commit` blieb bewusste, manuelle Eingabe des Einreichers – keine
  automatische Herleitung wurde eingeführt.

### 3. Technischer Nachweis

- Änderung: `THE PLATFORM/src/components/Workspace/Workspace.tsx`
- Commit: `9bfab3f` – UI - add submission creation from platform
- Echter Test: Submission `S-0012` erzeugt, Pull Request `#26` erstellt
  (`https://github.com/Gochness/Atlas/pull/26`), Repository-Pfad
  erfolgreich durchlaufen und serverseitig verifiziert (`gh pr view`,
  Dateiinhalt auf dem gepushten Branch geprüft).

### 4. Architekturentscheidung

- Mensch/KI entscheiden weiterhin bewusst, wann aus Beiträgen ein
  Ergebnis entsteht – kein automatischer Trigger.
- Keine automatische Synthese von WorkSteps zu Submission.
- Keine automatische `base_commit`-Ermittlung.
- Keine neue Diskussionsstruktur eingeführt.

Begründung: Ungeklärte epistemische Fragen wurden nicht durch Code
versteckt.

### 5. Ergebnis

Atlas kann erstmals eine vollständige Schleife durchführen:

```
Beitrag
→ WorkStep
→ gemeinsamer Arbeitsstand
→ Submission
→ Repository-Artefakt
```

### 6. Offene Punkte

- `base_commit`-Semantik bleibt eigener Klärungsfaden.
- Sichtbarkeit von offenen Submissions vor Merge ist zukünftige
  Architekturfrage.
- Strukturierte Beziehungen zwischen Beiträgen fehlen weiterhin.

### 7. Abschlussbewertung

Der Meilenstein beweist nicht die vollständige KI-Zusammenarbeit, aber
den ersten funktionierenden Weg von gemeinsamer Arbeit zu dauerhaftem
Artefakt.
